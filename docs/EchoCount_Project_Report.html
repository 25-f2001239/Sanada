Abstract

Estimating the number of simultaneously active sound sources in a single-channel audio mixture, identifying each acoustic event, and isolating clean stems remains a challenging signal-processing problem. While prior research demonstrates strong offline accuracy inside isolated notebooks, real-world adoption is limited by the lack of calibrated uncertainty reporting, open-vocabulary sound recognition, stem quality verification, and accessible web/mobile deployment. This report documents the end-to-end engineering of EchoCount (SANADA), a full-stack web and mobile-responsive acoustic intelligence platform.

The system is backed by a deduplicated corpus of 15,559 active audio mixtures (15,757 raw clips spanning 2–31 overlapping speech and FSD50K everyday sound sources across 13 active folders, with 198 exact-hash duplicates removed and 3 speakers strictly held out for unseen-speaker testing). A unified 16 kHz mono front-end computes a shared [1, 64, 501] Log-Mel spectrogram and fans it out across three parallel PyTorch and HuggingFace inference branches: (1) a custom-trained SourceCountCNN with 30-pass Monte Carlo Dropout and validation calibration; (2) an open-vocabulary tagger fusing a custom dual-head GroupFineTaggerCNN (0.9926 group test mAP) with pretrained AST (527 classes) and CLAP; and (3) ECAPA-TDNN speaker diarization paired with SepFormer (2–3 speakers) and a sharpened IterativeMaskSeparator guarded by correlation, energy-conservation, and re-tagging quality gates.

The application is served via Flask, Waitress WSGI, SQLite (Argon2id + Google OAuth 2.0/OIDC, RBAC Admin Dashboard, per-user History, SHA-256 ground-truth comparison, and a Live 2D Neural Architecture Visualizer), and deployed publicly on AWS EC2 Windows Server 2019 with automatic Caddy HTTPS and boot-level persistence. Shared spectrogram caching achieves a 2.70× core latency speedup (175.3 ms to 65.0 ms), and automated regression tests confirm functional, security, and isolation guarantees.

Chapter 1: Initiation, Problem Statement & Literature Survey (Week 1)

1.1 Problem Statement & Application Scope

Single-channel acoustic mixtures frequently contain multiple overlapping human voices and environmental sounds. Counting active sources (K) is an essential precursor to blind source separation, meeting analytics, and acoustic scene monitoring, yet most neural models reside in static research notebooks without calibrated confidence intervals, open-vocabulary labels, or stem verification. EchoCount bridges this gap by accepting single-channel audio (WAV, FLAC, MP3, OGG, M4A up to 40 MB / 600 s) and outputting: (i) an estimated source count with decomposed epistemic (MC-Dropout) and aleatoric (softmax) uncertainty; (ii) open-vocabulary sound labels with frame-level time ranges across 559 classes; and (iii) quality-gated separated WAV stems plus an exact energy-conserving residual.

Selected Enhancements: (a) 3-model open-vocab tagging fusion, (b) automated near-copy correlation, energy, and re-tagging quality gates, (c) live 2D Neural Architecture Visualizer (desktop & phone portrait + chimes), (d) Argon2id + Google OAuth RBAC & Admin Dashboard, and (e) SHA-256 ground-truth verification.

Bulk indexing across 15,559 files verifies duration integrity, SHA-256 uniqueness, and harmonic-percussive separation (HPSS) characteristics.

Chapter 2: Dataset Collection, Organization & Preprocessing (Week 2)

2.1 Dataset Identification & Verification

EchoCount utilizes the SANADA Combined Acoustic & Speech Mixtures corpus alongside a held-out FSD50K Isolated Subset (480 clips across 16 everyday sound classes, Zenodo 4060432, CC-BY). Automated auditing in data.py scanned all 14 mixture folders, identified 15,757 raw WAV mixtures, and verified file integrity and exact content uniqueness via SHA-256 hashing. One redundant folder (Org_Fsd_Mix/Org_Mix_4_Sounds_Variable) and 198 exact-hash duplicate mixtures were excluded prior to splitting, leaving 15,559 clean active mixtures (15,341 unique hashes) spanning 2 to 31 simultaneous sources across 5 coarse acoustic groups and 32 fine FSD domain classes.

2.2 Folder Architecture & Zero-Leakage Splits

Each mixture family (FSD_Mix_{2,3,15,20,25,Variable}_Sounds and Org_Mix_{2,3,4,6,9}_Sounds) contains isolated train/, val/, and test/ directories paired with a metadata.csv schema (mixture_path, num_speakers/num_sources, speaker_labels, source_files). Fixed random seed 42 ensures deterministic reproducibility. To evaluate true speaker generalization without identity leakage, 3 of the 13 unique speakers (Speaker_4_1, Speaker8, Speaker9; n = 352 mixtures) are strictly isolated in a held-out unseen-speaker split. Ground-truth verification in production uses an indexed SHA-256 registry (data/ground_truth_index.json, 15,559 entries) rather than filename heuristics.

2.3 Preprocessing & Augmentation Pipeline

Every audio file passes through a deterministic preprocessing pipeline enforced identically during training (scripts/train.py) and live inference (audio.py), with checkpoint metadata assertions preventing feature drift. During training, SpecAugment time/frequency masking, random gain perturbation, and balanced class sampling mitigate sparse-vs-dense imbalance, sustaining PyTorch DataLoader throughput above 12 batches/sec on CPU.

Chapter 3: Web/Mobile Application Architecture & Model Hosting (Week 3)

3.1 System Architecture & Data Flow

EchoCount implements a clean 3-tier architecture separating the responsive web/mobile client, the Python/Flask REST API and RBAC layer, and the 3-branch PyTorch + HuggingFace inference engine. Heavy stem separation is decoupled onto a background ThreadPoolExecutor so analysis responses return in ~1.7 s while separation jobs stream status via polling.

Figure 3: Three-Tier System Architecture Connecting Responsive Clients, Authenticated Flask API, and the 3-Branch ML Engine.

3.2 Frontend & Mobile UI Strategy

The frontend uses semantic Jinja2 templates, modular vanilla ES6 JavaScript, and responsive CSS Grid/Flexbox with dedicated tablet (≤ 760px) and phone (≤ 520px) breakpoints. Mobile constraints are explicitly addressed: (i) zero horizontal overflow (overflow-x: clip), swipeable horizontal tab strips, and full-width 50/50 touch buttons; (ii) the Live 2D Architecture Canvas switches dynamically from a 1200×620 horizontal desktop view to a native 440×1272 vertical portrait diagram on phones; (iii) long tag lists and Ground Truth chip groups render inside compact scrollable containers; and (iv) boot-stamped cache-busting query parameters (?v={{ asset_v }}) ensure mobile browsers always fetch current assets.

Chapter 4: Full-Stack Integration, Multi-Role UI & Cloud Deployment (Week 4)

4.1 Multi-Role Frontend Architecture

EchoCount enforces strict server-side and template-level separation between anonymous visitors, authenticated end-users, and administrators:

  • End-User Prediction Portal (/analyze, /history): Supports drag-and-drop uploads, synthetic 1–4 source test generators, interactive waveform playback, and a toggle between Analysis View (instant ~1.7 s results, Ground Truth comparison, on-demand stem separation) and Live Architecture View (choreographed 1 s/step signal visualization with custom step & completion chimes). /history displays strictly the logged-in user's analyses with search, CSV export, and per-account clearing.
  • Administrator & Evaluation Portal (/admin, /evaluation): Hidden from non-admins (returning HTTP 404 on pages and 403 on APIs). Provides 5 tabs: Overview (DAU/WAU, active sessions, 14-day bar charts, K-histogram, GT accuracy), Users (promote/demote admins, pre-authorized email invites, disable/sign-out/delete, CSV export), Activity (cross-user analysis stream), Audit Log (immutable admin action trail), and System (uptime, checkpoints, index count, storage). /evaluation renders held-out scatter plots, per-K tables, and real-room benchmarks.
  • Supporting & Analytical Pages (/, /how, /docs): Present interactive methodology walkthroughs, dataset audit tables, and REST API documentation backed by evaluation/public_summary.json.

4.2 Full-Stack API Wiring & Cloud Deployment Stack

Asynchronous XHR/Fetch calls drive live upload progress bars, stage badges (Decode → Count → Tag → Separate → ZIP), error toasts, and CSRF-protected mutations. For public cloud hosting, the application is deployed on an AWS EC2 Windows Server 2019 instance (t3.large, 8 GB RAM, Elastic IP 54.166.236.211) behind a Caddy reverse proxy providing automatic Let's Encrypt TLS on https://54-166-236-211.nip.io. Flask runs under Waitress WSGI (4 threads, trusting Caddy's X-Forwarded-* headers via ProxyFix), and two Windows SYSTEM boot tasks (EchoCountServer and EchoCountHTTPS) guarantee automatic startup after any EC2 stop/start or reboot without RDP login.

5.2 Inference Latency Optimization & Model Benchmarks

Profiling revealed redundant Mel-spectrogram recomputation between the Counter and Domain Tagger plus synchronous blocking during separation. Sharing one precomputed [1, 64, 501] Log-Mel tensor across branches and moving separation to on-demand background execution reduced core /api/analyze compute from 175.3 ms to 65.0 ms (2.70× speedup). On the 1,285-clip held-out test set, EchoCount achieves Speech MAE 0.80 (78.9% within ±1), Group Tagging mAP 0.9926, Fine 32-Class mAP 0.8052, and AST+CLAP Open-Vocab AP 0.9068.

5.3 UI/UX Refinements & Security Audit

Post-Week-4 refinements eliminated CSS Grid overflow on long code blocks, fixed dark-mode toggle button contrast, omitted distracting (±1) bands for small predictions (K ≤ 4), replaced long overlap lists with scrollable chip boxes, and sharpened query separation masks (neural weight 0.10 → 0.35, exponent 2.2 → 3.8). Security audits verified strict input extension/size/duration caps (40 MB / 600 s), sliding-window auth & API rate limits, CSRF token validation, HttpOnly Secure cookies, and zero secrets in git history.

Chapter 6: Conclusion & Future Work (Cluster Migration Roadmap)

6.1 Conclusion

EchoCount (SANADA) demonstrates that multi-model acoustic research pipelines can be operationalized into a reliable, transparent, and mobile-ready full-stack web application. By combining a custom-trained uncertainty-aware counter (SourceCountCNN), a 559-class open-vocabulary tagger fusion, and quality-gated speech/general separation behind a secure Flask/Waitress/Caddy stack on AWS EC2, the system delivers fast single-clip inference (~1.74 s), honest failure reporting when spectral overlap saturates (K ≥ 9 or near-copy stems r > 0.90), and complete administrative observability.

6.2 Future Work — 9-Node Hadoop & Spark Cluster Migration

While the single-node AWS EC2 deployment handles interactive single-clip requests smoothly, institutional-scale batch processing (thousands of multi-minute recordings) and periodic full-corpus retraining require distributed storage and compute. The planned migration maps EchoCount onto the institutional 9-Node Hadoop & Spark Cluster:

  • Web/API Gateway & Shared Environment (slave4 — 192.168.5.104): Hosts the Flask/Waitress gateway using the centralized NFS Anaconda Python stack (/home/hduser/anaconda3), migrating relational user/audit/history tables from local SQLite to the centralized kmit-database node (192.168.5.102).
  • 4 TB HDFS Vault (Name Node — 192.168.5.100): Stores raw audio corpora, versioned PyTorch checkpoints (*.pt), HuggingFace model archives, and large-scale batch separation outputs with HDFS replication.
  • Distributed Training & Batch Inference (YARN 192.168.5.101 & Spark Master 192.168.5.103): Heavy retraining and bulk folder inference jobs are submitted asynchronously from the gateway via spark-submit to YARN/Spark Master and partitioned across the active worker fleet (slave4–slave7), writing aggregated JSON results back to HDFS and kmit-database.
